# ADR-0002: Markdown — единственный источник правды

**Статус:** Принято
**Дата:** 2026-07-29

## Контекст

Содержание курса нужно одновременно в нескольких местах: как читаемые файлы (GitHub/редактор), на сайте (карточки, поиск, дни), в статистике. Риск: если хранить контент в двух форматах (напр. Markdown + JSON для сайта), они неизбежно разъедутся.

Варианты: (а) вести контент отдельно для чтения и отдельно для сайта; (б) хранить в JSON/БД, а Markdown генерировать; (в) хранить в Markdown, всё остальное генерировать из него.

## Решение

**Markdown-файлы курса (`ru/`, `tg/`) — единственный источник правды.** Всё производное генерируется из них скриптами:
- `site/build-data.py` → `site/data.js` (данные сайта);
- `scripts/build_stats.py` → `STATS.md` (статистика).

Формат дня строгий (`### День N —`, маркеры `📺/📖 💻 ✍️ 🎯`), потому что по нему работает парсер.

## Последствия

**Плюсы:**
- Один источник — контент и сайт не разъезжаются by design.
- Markdown удобно писать, ревьюить в PR, переводить, читать без инструментов.
- Генерация детерминирована; CI проверяет, что артефакты пересобраны ([ci.yml](../../.github/workflows/ci.yml)).

**Минусы / компромиссы:**
- **Формат дня нельзя ломать** — иначе парсер не соберёт данные. Это правило вынесено в [TRANSLATION_GUIDE.md](../../TRANSLATION_GUIDE.md) и [RELEASE_CHECKLIST.md](../../RELEASE_CHECKLIST.md).
- Нужен шаг генерации после правок (митигируется CI-проверкой и Docker-командой).
- Парсер на регэкспах чувствителен к структуре (сознательный компромисс ради простоты — без AST-парсера Markdown).

**Что это закрывает на будущее:**
- Любой новый потребитель контента (мобильное приложение, LMS-пакет) читает те же Markdown или генерируемый `data.js` — не появляется второй источник правды.
